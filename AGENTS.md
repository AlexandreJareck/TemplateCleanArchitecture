# TemplateCleanArchNET agent guide

## Repository purpose

This is an academic .NET Clean Architecture template. The executable system is an ASP.NET Core Web API with PostgreSQL persistence, ASP.NET Core Identity/JWT authentication, Redis caching, RabbitMQ messaging, an Elasticsearch person index, Serilog (console plus an optional Elasticsearch data-stream sink), localization, OpenAPI, and health checks. A separate legacy VSIX project packages the template for Visual Studio.

Use `docs/product/` (Phase 23 blueprint: glossary, domain model, business-rule catalog with stable IDs, workflows, permissions, API guidelines, frontend architecture, NFRs, event catalog, decision log, ADRs) as the authoritative product design for Phases 24–33. Use `docs/phase-2-workspace.md` for the proposed AI workspace, target architecture, dependency upgrade matrix, and coding standards. Use `docs/phase-3-implementation-plan.md` for the staged refactoring plan. Decisions adopted on 2026-10-10 are at the end of the Phase 3 plan. Re-check external versions before implementing upgrades; the recorded versions were verified on 2026-10-08.

Agent skills have a single source in `.agents/skills/` (read by Codex). Claude Code reads them through a git-ignored `.claude/skills` link created by `powershell -ExecutionPolicy Bypass -File .\scripts\link-agent-skills.ps1` (run once per checkout, idempotent). Edit skills only in `.agents/skills/`.

## Repository language and file naming

- Name source files, scripts, configuration files, agent instructions, technical documentation, and their directories in English.
- Write code, code comments, identifiers, agent-facing instructions, and technical documentation in English.
- Human-facing functional or product documentation may be written in Brazilian Portuguese when its intended audience benefits from it, but its filename must still be English.
- Culture-qualified localization resources such as `*.pt-BR.resx` keep their standard culture identifier; this is not considered a Portuguese filename.
- When an `AGENTS.md` exists in a directory, keep a sibling `CLAUDE.md` that references it with `@AGENTS.md` so both agents use the same local instructions.

## Current implementation conventions

- Controllers inherit `BaseApiController`, use URL-segment API versions, MediatR for product use cases, `BaseResult`/`PagedResponse`, and `CustomResponse` for error mapping. v1 and v2 are inconsistent; treat v2 as the closer baseline, not as a finished standard.
- Phase 24+ endpoints follow `docs/product/api-guidelines.md`: explicit kebab-case `[Route]`, plain representations (`Result<T>` mapped by `ApiResultMapper.ToActionResult(result, HttpContext, ...)`), `PagedResult<T>`, `[StableProblemCodes]` (Problem Details `code`), `[ProblemCodes(...)]`, `[NoStoreSecurityHeaders]`, and authorization by `[HasPermission(Permissions.X)]` (never role names), `[Authorize]` or `[AllowAnonymous]` on every action (architecture-tested).
- Product use cases co-locate request, handler, and validator in feature files. Handlers depend on repository/application interfaces and return result wrappers rather than throwing expected business errors.
- Entities expose private setters and behavior methods, inherit `BaseEntity` or `AuditableBaseEntity`, and use EF-compatible private constructors. Preserve invariants inside entities; do not turn them into public-setter persistence bags.
- Persistence implements application-owned ports with EF Core repositories and a unit of work. PostgreSQL/Npgsql is the active relational provider. Async ports accept `CancellationToken`; handlers use `IClock` for observable time and a MediatR `ValidationBehavior` runs FluentValidation validators.
- DI registration is split by project in `ServiceRegistration.cs`; WebApi is the only composition root.
- Tests use xUnit 2.9.3 (VS runner 3.1.5), Shouldly, and Moq 4.21.0 with `Microsoft.NET.Test.Sdk` 18.10.1; `coverlet.collector` 10.1.0 (Cobertura) is referenced only by the unit, integration and functional projects and every test-tooling package stays test-only with `PrivateAssets=all` (Phase 19). Unit tests isolate handlers, integration tests exercise EF repositories and adapters, `Tests/Template.RabbitMq.Integration.Tests`, `Tests/Template.Elasticsearch.Integration.Tests` and `Tests/Template.Redis.Integration.Tests` exercise real services, functional tests exercise HTTP endpoints (plus health-check and logging bootstrap), and `Tests/Template.Architecture.Tests` enforces dependency rules.
- Nullable settings are inconsistent across projects. New code should enable nullable reference types and avoid adding `#nullable disable`.

## Change and validation rules

- Keep Domain free of framework, transport, database, cache, broker, logging, and search dependencies.
- Put use-case orchestration and ports in Application; put EF Core, Identity, Redis, RabbitMQ, Elastic, and localization implementations in Infrastructure; keep WebApi focused on HTTP and composition.
- Preserve API compatibility deliberately. Do not silently remove v1 or change routes/status codes; document and test any deprecation path.
- Add or update tests with each behavior change. Run the smallest relevant green commands above, then broader validation when dependencies are available.
- Run build/test commands sequentially because parallel builds contend for shared `obj` outputs.
- Do not add package versions from memory. Verify stable versions and migration notes using official sources, update related package families together, and pin Docker images to explicit versions or digests.
- Treat migrations and integration upgrades as reversible steps. Never rewrite an applied migration merely to clean it up.
- Never commit secrets. Committed appsettings, launch profiles, Compose files and `.env.example` carry no secret value (enforced by `CommittedSecretsTests` and `scripts/secret-scan.ps1`); `.env` and user secrets hold the real values. Document only configuration key or environment-variable names, and use `docs/configuration-secrets.md` for setup and rotation.
- Do not edit generated EF migration designer/snapshot files or generated `.resx` designer files by hand.
- Do not hand-edit `graphify-out`; regenerate it with Graphify after structural code changes.
- Preserve unrelated user changes and do not use destructive Git commands.
