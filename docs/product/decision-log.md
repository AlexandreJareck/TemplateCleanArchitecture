# Decision log

All D23 decisions were presented with their recommended defaults on 2026-10-18 and the owner explicitly answered "accept all recommended" for D23-1 through D23-18. No default was adopted silently. Decisions taken by the blueprint itself (B23-*) are design choices that refine an owner decision without changing it; they can be changed by a later owner decision recorded here.

## Blueprint decisions (refinements, 2026-10-18)

| ID | Decision | Refines | Rationale |
|---|---|---|---|
| B23-1 | Approval is an **award approval**: one approval instance per requisition, started when the buyer submits an award (competitive or direct). There is no separate pre-sourcing requisition approval. | D23-4, D23-13 | Matches the roadmap sequence (comparison → approval → PO) and D23-4 (confirm on final approval). |
| B23-2 | Besides D23-13, the same user cannot decide two levels of the same approval instance, and the buyer who submitted the award cannot give the final approval (APR-007, APR-008). | D23-13 | Standard maker-checker; adjustable only by a new owner decision. |
| B23-3 | Direct purchases use the same RFQ aggregate with `SourcingMethod = Direct` and a waiver, so quote, award, approval and PO handling are uniform. | D23-14 | Avoids a parallel path that would duplicate rules. |
| B23-4 | Organization base currency is BRL (installation setting); cross-currency quotes are normalized with a persisted PTAX selling-rate snapshot or a permission-protected manual rate. | D23-17 | Deterministic comparison; never a live rate. |
| B23-5 | The organization time zone is `America/Sao_Paulo`; all instants are stored in UTC; dates such as needed-by and fiscal boundaries are local dates in the organization time zone. | D23-17 | Fiscal periods and deadlines need one calendar. |
| B23-6 | Late quotes are rejected; the buyer may extend the RFQ deadline before it passes (reason required). No late-quote waiver. | D23-14 | Smaller rule surface. |
| B23-7 | Rejection is terminal for the requisition; the requester can copy it into a new draft. Withdrawal (before an RFQ is published) returns it to Draft with a new revision. | D23-4 | Keeps approvals immutable. |
| B23-8 | New procurement endpoints return plain resource representations and a `PagedResult` envelope, not `BaseResult`; existing v1/v2 sample endpoints are unchanged. | API compatibility | See [api-guidelines.md](api-guidelines.md). |
| B23-9 | Roles group permissions; authorization checks permissions only; no role is a business-rule bypass (including Administrator). | D23-13 | Required by the Phase 24 handoff. |
| B23-10 | Seeded policy values in this blueprint are policy version 1 and are owner-adjustable data; a change creates a new version and never alters in-flight instances. | D23-13, D23-14, D23-17, D23-18 | Versioned policy requirement. |
| B23-11 | Approval policy v1 uses 120 h step duration and a 72 h reminder (calendar hours), instead of the first draft's 72 h / 48 h, so a step opened on a Friday does not escalate over the weekend. Approved by the owner on 2026-10-18. | D23-13 | No business-day calendar in the first release. |

## Phase 24 implementation decisions (2026-10-18)

Design choices made while implementing D23-11 and SEC-001..010 in Phase 24. They refine the blueprint without changing an owner decision; details and evidence are in `docs/refactoring/phase-24-report.md`.

| ID | Decision | Refines | Rationale |
|---|---|---|---|
| D24-1 | `POST /api/v2/auth/sessions` verifies credentials without signing in and **does not rotate the security stamp**; the legacy `authenticate`/`start` routes keep rotating it on every sign-in, which revokes v2 families at their next refresh and rejects their access tokens immediately. | SEC-001, SEC-006 | Several concurrent sessions (SEC-010) are impossible if every login invalidates the others; the legacy behavior is preserved deliberately. |
| D24-2 | Session families, refresh-token hashes, audit records and idempotency records live in the **application database**; Identity keeps users, roles and role claims. | AUD-001, ADR-0001 | Session changes and their audit records commit together, and later procurement changes can share the same audit table in one transaction. Password-change revocation crosses databases, so it is enforced twice: by the stamp binding and by an explicit revoke-all after the Identity commit. |
| D24-3 | The CSRF HMAC key is derived with HKDF-SHA256 from `JwtSettings:Key` (info `template.session.csrf.v1`); **no new secret** is introduced. | NFR-SEC-1, api-guidelines §7 | Key separation without another secret to provision; rotating the signing key also rotates every CSRF binding. |
| D24-4 | Access tokens issued by a session carry the registered `sid` claim (family ID); bearer validation rejects them as soon as the family is revoked or expired. Legacy tokens have no `sid` and are unaffected. | SEC-006 | Logout and revoke-all take effect immediately instead of after the 15-minute token lifetime. |
| D24-5 | Login answers `200 OK` (credential exchange, like an OAuth token endpoint), not `201`. | api-guidelines §2 | No addressable session resource is returned. |
| D24-6 | SEC-007 uses `System.Threading.RateLimiting` fixed-window partitions inside an action filter on the two endpoints (login: IP + normalized user name; refresh: IP), with SHA-256 partition keys. | SEC-007 | The user-name partition needs the bound body; no other endpoint is affected. |
| D24-7 | The stable `code` extension is added only to Problem Details of Phase 24+ endpoints (marker attribute); legacy v1/v2 bodies stay byte-compatible. `ErrorCode` gains values 6–11 (appended). | api-guidelines §5, §10 | Contract compatibility. |
| D24-8 | **SP-1 closed:** explicit `bigint Version` concurrency token on `VersionedAggregateRoot`; a guard unique index (`AccessRefreshTokens(FamilyId, Sequence)`) violated by a concurrent writer is translated to the same `ConcurrencyConflictException`. | SP-1 | Proven by the PostgreSQL concurrency tests and the 412/428 functional test. |
| D24-9 | The seeded default user receives **no** role; roles are seeded with their permissions only when missing, and the legacy `Admin` role grants no permission. | B23-9, B23-10 | The default user's password is a committed sample value; assigning roles is Phase 25 user management. |
| D24-10 | `Idempotency-Key`, `If-Match`/`ETag` and `202 Accepted` are reusable primitives exercised by a test-only fixture controller; the first production adopters arrive with Phase 25 resources. Session endpoints never use idempotency storage (it would persist tokens). | api-guidelines §4, §6, §8 | Avoids speculative production endpoints. |

## Phase 25 implementation decisions (2026-10-18)

Design choices made while implementing ORG-*, SUP-*, CAT-* and INT-001/002 in Phase 25. They refine the blueprint without changing an owner decision; details and evidence are in `docs/refactoring/phase-25-report.md`.

| ID | Decision | Refines | Rationale |
|---|---|---|---|
| D25-1 | Aggregate behavior methods return a `DomainError` (code, kind, rule ID, field) for expected rejections and throw only for programming errors; Application maps the kind to 400/404/409/422. | Core instructions, api-guidelines §5 | Handlers return results instead of throwing business errors; rule IDs reach Problem Details. |
| D25-2 | Codes are trimmed and stored upper-cased, so the plain unique indexes are case-insensitive (ORG-001). Formats: departments/cost centers `^[A-Z0-9-]{2,20}$` (ORG-001); categories/units `^[A-Z0-9-]{1,20}$`; catalog items `^[A-Z0-9][A-Z0-9._-]{0,39}$` (CAT-001 left the format open; SKUs need dots/underscores). | ORG-001, CAT-001 | No `citext` extension or functional index; one representation everywhere. |
| D25-3 | SUP-001 accepts the **alphanumeric CNPJ** (IN RFB 2.229/2024, issued from July 2026): 12 upper-case letters/digits plus 2 numeric check digits, modulo 11 with each character valued as its ASCII code minus 48; repeated-digit values are rejected. Purely numeric CNPJs are the special case without letters. | SUP-001 ("digits only for BR") | Rejecting valid new CNPJs would block real suppliers; the check is still structural only. |
| D25-4 | Contacts and addresses are replaced as whole collections (`PUT /suppliers/{id}/contacts`, `/addresses`, `/categories`) under the supplier's single version token; entries with `id` are updated, without are added, missing are removed, atomically. A non-draft supplier can never lose its last contact with email, its last address or its last category (SUP-002 re-checked). | api-guidelines §1, SP-1 | One aggregate, one ETag; no partially applied child edits. |
| D25-5 | Country and tax ID are editable only while the supplier is `Draft` (typo fix before activation); afterwards they are identity. | SUP-001 | Keeps snapshots taken by later modules meaningful. |
| D25-6 | Reasons are 10–500 characters: the minimum matches the waiver reason minimum, the maximum the `AuditRecord.Reason` column. | SUP-005, ORG-003 | One rule for every reason field. |
| D25-7 | Deactivation of departments, cost centers, categories, units and catalog items requires a reason (ORG-003 extended to the Catalog module, CAT-002); master-data reactivation records an optional reason. Supplier suspend/inactivate/reactivate always require one (SUP-005). `Reactivate` covers both `Suspended → Active` and `Inactive → Active`. | ORG-003, CAT-002, SUP-005, workflows §7 | Uniform audit history; the workflow table has no separate "resume" transition. |
| D25-8 | A unit's `AllowedDecimals` is fixed at creation. | CAT-003 | Quantities already recorded in the unit stay valid. |
| D25-9 | Optional providers live in the new `Template.Infrastructure.Integrations` project, are **disabled in every committed profile** and replaced by a disabled adapter in the Test environment. Resilience is implemented in-house (per-attempt timeout 5 s, at most 2 retries only for timeout/network/408/5xx, no retry on 429, 5-failure/30 s consecutive-failure circuit breaker with one half-open trial) instead of `Microsoft.Extensions.Http.Resilience`/Polly; the only new package is `Microsoft.Extensions.Http` 10.0.13 (same servicing family as the repository). The default `HttpClient` request logging is removed because URLs carry the CNPJ/CEP. | INT-001, ADR-0007, NFR §9 | Deterministic fake-server tests, minimal package graph, no identifier in logs. |
| D25-10 | Lookups return an advisory proposal (provider, retrieval instant, normalized values, notice) and store nothing; acceptance (`POST /suppliers/{id}/enrichment-acceptances`) carries the proposal's provider (allow-listed) and `retrievedAt` (not in the future, at most 24 h old) plus the values the user accepted or edited, which go through the ordinary supplier invariants. The snapshot stores provider, retrieval and acceptance instants, accepting user, accepted field names, registration status and the accepted names/postal code. No proposal cache exists because no freshness/privacy rule for caching was approved. | INT-002, ADR-0007 | Provenance without trusting live data; nothing read live afterwards. |
| D25-11 | Provider contact data (emails, phones, partners) is never mapped by the adapter. | NFR §9, SUP-006 | Data minimization: enrichment needs registration and address data only. |
| D25-12 | SP-5 starting point implemented as an Application service: one PTAX request for `[date − 7 days, date]`, the latest bulletin whose `tipoBoletim` starts with `Fechamento`, selling rate with at most 6 decimals; none in the window → `NotFound` (comparison incomplete, SRC-013). No HTTP endpoint in Phase 25; Phase 29 consumes the port. | SP-5, CALC-004 | One bounded call instead of day-by-day probing. |
| D25-13 | ORG-004 is enforced through an `IOrganizationSettingsLock` port whose Phase 25 adapter answers "no allocations" (the Budgeting tables arrive in Phase 27, which replaces the adapter). | ORG-004 | The rule and its tests exist now; the data source arrives later. |
| D25-14 | `GET /api/v2/users` (`access.users.manage`) returns ID, user name, display name and active flag for ORG-006 assignments; "active" means the Identity user exists and is not locked out. User/role administration endpoints are deferred (not in the Phase 25 handoff). | ORG-006, roadmap Phase 24 note | Unblocks manager/head assignment without widening the identity surface. |
| D25-15 | Audit actions: `organization.department.*`, `organization.cost-center.*`, `organization.settings.changed`, `catalog.{category,unit,item}.*`, `supplier.created/updated/contacts-changed/addresses-changed/categories-changed/enrichment-accepted` and one action per transition (`supplier.activated/suspended/inactivated/reactivated`, with from/to state, reason and rule IDs). `AuditRecord` detail keys gain `code`, `fields`, `provider`, `departmentId`, `categoryId`, `unitOfMeasureId`; tax IDs, names, contacts and addresses never enter details. The `procurement.supplier.status-changed` integration event waits for the Phase 28 Outbox; APR-012 invalidation is Phase 31. | AUD-001, AUD-003, event catalog | Precise, allow-listed history now; events when the Outbox exists. |
| D25-16 | The unit of work translates only the business-key unique indexes (codes, supplier tax ID) into `UniqueConstraintViolationException`; primary-key and other violations keep their original exception. | ORG-001, CAT-001, SUP-001 | Concurrent duplicates become 409 without changing Phase 24 failure semantics. |
| D25-17 | Procurement enums (`Template.Domain.Catalog/Suppliers/Organization`) are documented as strings in OpenAPI by a namespace-limited schema filter; legacy schemas such as `ErrorCode` keep their integer form. `ErrorCategory.Unavailable` (503) is appended; `ErrorCode` is unchanged. | api-guidelines §2, §5, §10 | Generated clients (Phase 26) match the wire format; legacy contract untouched. |
| D25-18 | Tables follow the Phase 24 convention (PascalCase with module prefix: `OrganizationDepartments`, `OrganizationCostCenters`, `OrganizationSettings`, `Suppliers`, `SupplierContacts`, `SupplierAddresses`, `SupplierCategories`, `SupplierStatusChanges`, `CatalogCategories`, `CatalogUnitsOfMeasure`, `CatalogItems`), and a module's Domain references another module's aggregates by ID plus a `MasterDataReference` (ID, active) only. | domain-model §1, ADR-0001 | Consistency with the existing schema; enforced by an architecture rule. |
